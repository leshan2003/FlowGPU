## 一、结论先行

本次已经完成 MoE v2 仿真平台、完整实验矩阵、结果审计和仓库整理，并同步到
GitHub。

最重要的结论：

1. 当前最稳定的方案是 **HBM 保留全部专家 + 类脑 SRAM 选择性保存热点副本**。
2. **Coverage-first 是最稳的规划 baseline**；固定 replica-first 收益普遍较弱。
3. GPU/Brain 并行 overlays **只在高 batch 和合适 scheduler 下有明确收益**，
   低/中 batch 不会自动获益。
4. D0 GPU-direct 明显降低 bridge 流量，但 completion 收益依赖 batch 和网络瓶颈。
5. D0 聚类降低 node cut，却没有稳定改善 completion；当前不能把“聚类有效”
   作为论文结论。
6. 全类脑 DRAM/SRAM 的 M1 在当前 projected profile 下显著慢于 GPU/HBM。
7. 对标 DeepInfer EPLB 后，负载均衡机制已实现；但当前 Brain 副本预算远
   小于专家数，优先 coverage 仍比预留 12.5%–50% 热点冗余副本更快。

当前不能声称：

- KA200 实测性能；
- 真实 router popularity 或真实任务漂移；
- 真实 TCO；
- 某一固定刷新周期；
- 聚类在真实 trace 中一定有效。

## 三、主要实验数据

### 20-seed 固定配置

```text
2 Brain nodes
batch 2
16 copies
C = 2
```

| 场景 | Coverage 完成时间 | Overlay SLO 吞吐 |
|---|---:|---:|
| Mixtral Zipf 0.5 | 1.053× | 1.026× |
| Mixtral Zipf 1.3 | 1.085× | 1.033× |
| Mixtral Zipf 2.0 | 1.081× | 1.036× |
| Qwen 四层 | 1.112× | 1.085× |
| DeepSeek 四层 | 1.081× | 1.074× |
| gpt-oss 四层 | 1.176× | 1.051× |

解释：

- Coverage 比较的是总完成时间；
- Overlay 比较的是 SLO 合格请求吞吐；
- 两列不能直接相减；
- Qwen/DeepSeek/gpt-oss 只覆盖前 4 个 MoE 层。

### GPU/Brain 并行

高 batch 四层专项：

```text
Mixtral 前 4 层
2 nodes
batch 64
10 paired seeds
```

结果：

- M2 的 D0 比 D1 快约 3.9%，CI `[1.0244, 1.0528]`；
- D0 下 M3 `earliest_finish` 比 M2 快约 8.2%，
  CI `[1.0085, 1.1556]`；
- D1 下 M3 比 M2 快约 11.6%，CI `[1.0408, 1.1908]`。

但低/中 batch 下 M3 不自动获益，部分 scheduler 会显著变差。

### D0 下 C

32-copy budget：

| Nodes | C=1 hot copies | C=2 | C=4 |
|---:|---:|---:|---:|
| 1 | 8 | 16 | 24 |
| 2 | 16 | 24 | 24 |
| 4 | 24 | 24 | 24 |

结论：

- C 的作用主要是限制 hot coverage；
- 4 nodes 时 C 完全不活跃；
- 2 nodes 时 C=2 与 C=4 布局相同；
- batch 增大会放大 hot coverage 的收益；
- 不存在“C 越大永远越好”。

### 聚类

- full-hyperedge 可以降低 node cut；
- 2-node、C=2/4、batch 1：node cut `11.8 → 5.4`；
- 但 completion 没有稳定改善；
- pair clustering 在多 node、高 batch 下反而慢约 3.7%–3.8%。

当前结论：

> D0 聚类机制有效，但当前 synthetic workload 中没有形成端到端收益。

### 全类脑 M1

完整 Mixtral 32 层 B-stage：

| Hot experts | Batch | M1 / GPU-only |
|---:|---:|---:|
| 8 | 1 | 0.0194× |
| 24 | 4 | 0.0313× |
| 24 | 64 | 0.1573× |

当前 projected HP300 配置下，M1 显著慢于 GPU/HBM。
这仍不是相同成本或功耗下的硬件结论。

## 四、审计中修正的重要问题

本次不是只多加结果，还修正了几处会改变结论的实现问题：

1. **D0 实际事件流曾被 home-node 污染**：
   预测走 D0，但实际 flow 仍经过 D1 home；
   现在预测和事件 flow 已统一。
2. **M2/M3 曾使用不同 placement**：
   现在 M3 继承 M2 的同一 hot/cold 位置，只增加 GPU hot 副本。
3. **早期 C 扫描没有形成有效约束**：
   已改为 32-copy budget，让 C 真正改变 hot coverage。
4. **原聚类微基准是退化对照**：
   三种算法实际布局相同；现已更换有区分度的 stress 和 D0 grid。
5. **早期 per-GPU 路由无效**：
   已改为 owner-GPU + 每个 GPU 全 expert 副本的合法模型。

## 五、当前证据边界

可以支持：

- synthetic/projected 条件下一系列可靠的机制结论；
- 完整实验可复现；
- D0/D1、M1/M2/M3、C、node、batch 和聚类都有明确控制；
- 负结果和失败对照已保留；
- canonical bundle 源码哈希一致。

不能支持：

- KA200 真机性能；
- 真实业务 workload 和 TCO；
- 完整模型 serving P99；
- 最终刷新周期；
- 真实 trace 下聚类一定有效。

## 六、下一步建议

优先级从高到低：

1. 接入真实 request-ordered router trace；
2. 补 KA200 kernel/NoC/DRAM/power 原始测量；
3. 实现全局 load-aware scheduler 和小拓扑 oracle；
4. 做完整模型 D0/D1 serving P99/SLO；
5. 研究 D0 聚类与真实共激活/home-affinity；
6. 为 M1 增加 block streaming、prefetch 和 overlap；
7. 在 coverage 饱和或更大多 expert 预算下复测两时间尺度 EPLB；
8. 获得价格/功耗后再做 TCO。

## 八、微信可直接发送版

> 学长，这次上传的不只是几组结果，而是一整套新的 MoE v2 仿真平台。它现在能模拟：专家在 GPU/HBM、类脑 DRAM 和类脑 SRAM 之间怎么放置；热点专家放几份副本；GPU 和类脑怎么分工、什么时候需要同时计算；同层经常一起出现的专家如何聚类；节点数、并发请求数和芯片容量 C 怎样影响性能；以及请求类型变化后，怎样检测变化、搬移专家并切换新布局而不打断正在处理的请求。还补了 DeepInfer 式专家负载均衡、连续请求仿真、多 seed 置信区间、源码哈希和可复现实验包，目前 47 组正式结果、151 项测试通过。

> 目前结论是：GPU/HBM 保留全部专家、少量热点专家再放到类脑，整体最稳；优先扩大不同专家覆盖，比只给热点重复加副本更有效；GPU 和类脑同时计算只在请求量较大时有明显好处；专家聚类能减少节点间通信，但暂时没有稳定提速；C 主要影响热点能覆盖多少专家，不是越大越好；全部专家都放类脑在目前参数下明显更慢；刷新、迁移和版本切换已经跑通，但完整长期刷新收益还没验证。现在仍是仿真结果，下一步需要真实请求数据和 KA200 实测。详细报告在 `docs/MOE/README.md`。

## 九、微信超短版

> 学长，这次上传的是整套新的 MoE v2 仿真平台：能模拟专家在 GPU HBM、类脑 DRAM/SRAM 间分层、热点副本、GPU/类脑协同、专家聚类、节点/并发数/C 的影响、专家迁移和布局刷新，并补了 DeepInfer 式专家负载均衡；目前 47 组正式结果、151 项测试通过。结论是：GPU/HBM 全量保底 + 热点专家放类脑最稳；Brain 副本预算不足时先覆盖不同专家，比给少数热点重复加副本更快；GPU 和类脑同时算只在请求多时有优势；聚类、全放类脑暂未看到稳定收益；刷新机制已跑通，但长期收益还需真实数据验证。文档在 `docs/MOE/README.md`。
