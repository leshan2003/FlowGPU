# 04 结论与缺口

## 1. 已支持

| 结论 | 条件 |
|---|---|
| HBM fallback + selective Brain overlay 有正收益 | projected HP300 + synthetic |
| Coverage 是最稳定 baseline | 20 paired seeds |
| node/batch 非单调 | Mixtral 9 点矩阵 |
| C 主要是 coverage/capacity 参数 | 32-copy D0 grid |
| D0 减少 bridge bytes | 相同 workload/plan |
| high-batch M3 可并行利用 GPU/Brain | 4-layer screen |
| per-GPU owner 模型可运行且有少量收益 | 每 GPU 全 expert 副本 |
| EPLB 可降低 Brain node/chip 内部负载不均衡 | 固定副本预算、Mixtral D0 |

## 2. 条件性结论

- **M3 并行收益**：high batch/合适 scheduler 成立，低/中 batch 不成立；
- **H-exclusive**：依赖于模型和 workload；
- **Joint vs Coverage**：模型依赖；
- **聚类**：node cut 可下降，但 completion 未稳定改善；
- **D0 vs D1**：低 batch 几乎相同，高 batch D0 有 3.9% 四层收益；
- **C**：容量不活跃时无效，活跃时改善 hot coverage；
- **EPLB**：当前容量下机制有效，但 coverage 收益更重要；覆盖饱和后才应
  优先考虑热点冗余副本。

## 3. 不支持

- “HBM 足够就不需要类脑”：有正收益，但包含新增 Brain 硬件；
- “全部放类脑更好”：当前 M1 显著更慢；
- “M3 自动优于 M2”：低/中 batch 和错误 scheduler 会退化；
- “聚类必然有效”：当前 D0 completion 无稳定收益；
- “C 越大越好”：4-node 时 C 完全无效；
- “per-GPU 必然更快”：request 固定绑定造成负载不均；
- “EPLB 降低 moe_lb 就等于端到端加速”：当前冗余策略稳定变慢；
- “DeepInfer 的冗余比例可直接搬到 FlowGPU”：两边 logical expert
  coverage 和硬件预算不同；
- 真实 KA200 性能、TCO、最小生产 node 数。

## 4. 当前架构建议

| 场景 | 建议 |
|---|---|
| 低/中 batch | HBM fallback + 少量 SRAM hot copies；不要强制 GPU 并行 |
| 高 batch | 测试 GPU/Brain 并行 M3，需要 load-aware scheduler |
| D0 | 聚类目标应优化 GPU bridge、专家 node fanout 和 combine |
| D1/D2 | 聚类目标必须加入 request-home affinity |
| 全 Brain | 只有在 DRAM/streaming/overlap 显著更好时再考虑 |
| per-GPU owner | 需要 GPU/request load balancing |
