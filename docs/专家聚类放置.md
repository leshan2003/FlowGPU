# MoE 专家聚类放置

> **审计状态（Simulator v2）**：本文是历史探索记录，不是真机实测报告。文中的
> “实测”均应理解为旧版解析模型的投影结果；`lynxi_hp300_proj` 和相关链路/带宽参数
> 没有仓库内 KA200 原始测量 artifact 支撑。固定阈值、最优 `C`、百分比收益和
> “复制收益为 0”等结论目前不可作为真机结论引用。可执行语义、证据等级和新实验契约
> 以 [`docs/sim_v2/README.md`](sim_v2/README.md) 为准。旧表格仅保留用于追溯假设。

## 一句话

把一层里"经常一起被激活"的专家放到同一颗芯片上，可以让一个 token 少往几颗芯片发数据。

**旧版解析模型曾给出的结论：只有在 batch 256 时才划算（省 25%）；该结论尚未由
v2 detailed 模型或真机复现。**

原因在第 5 节——"看起来能省很多"是建立在理想假设上的，现实里省不了那么多。

## 0 全局框架

> 本节是全文的地图。后面各节都是这张图的展开。

### 0.1 专家放置有三个独立旋钮

| 旋钮 | 是什么 | 取值范围 | 谁决定 | 效果落在哪个物理量上 |
|---|---|---|---|---|
| **① 放哪个池** | 热专家进类脑 SRAM、冷专家沉 GPU HBM | 二选一 | 模型（路由决定谁热）| 读权重的带宽 |
| **② 放哪颗芯片** | 一颗芯片放几个专家（C）| 1 – 15.5 | 编译器 | 计算串行度 |
| **③ 用哪些芯片** | 一层的芯片是否相邻 | 紧邻 / 散开 | 编译器 | 走哪条链路 |

**三个旋钮的效果分别落在三个不同的物理量上：**

```text
①  →  读权重的带宽    类脑 SRAM 51.2 TB/s  vs  GPU HBM 3.35 TB/s    差 15 倍
②  →  计算时间        每颗芯片串行算 C 个专家                         × C
③  →  链路            node 内 90 GB/s / 0.4 µs  vs  跨 node 39 GB/s / 7 µs
                                                     带宽差 2.3 倍，延迟差 17.5 倍
```

**三者不在同一个量上，所以不能直接比大小，必须折算到同一个总时间。** 本文后面所有表格都是在做这个折算。

### 0.2 三个"多对一"，性质完全不同

MoE 里有三个"多个对一个"的关系，常被混为一谈，但方向正好相反：

| 关系 | 性质 | 为什么 | 方向 |
|---|---|---|---|
| **多 token → 同一个专家** | **并行** | GEMM 的 M 维就是 token 数 | 越多越好 |
| **多专家 → 同一颗芯片** | **串行** | 一个专家就占满 256 个核 | 越少越好 |
| **多 token → 同一目的芯片** | **合并** | 同一份数据少发几份 | 越少越好 |

#### （1）多 token → 同一个专家：并行，而且是好事

一个专家就是一次矩阵乘 `M × N × K`，**M 就是分给这个专家的 token 数**。数据流阵列的效率是：

```text
填充率 = M / (M + pipeline_depth)
```

| batch | 每个热专家分到几个 token | 填充率 |
|---|---|---|
| 8 | 8 × 7.2 ÷ 51 ≈ 1.1 | 很低 |
| 256 | ≈ 36 | 中 |
| 1024 | ≈ 144 | 接近满 |

**所以"多个 token 命中同一个专家"不是串行——它正是大 batch 让类脑芯片变高效的原因。**

> 这条也解释了第 7 节那个现象：**计算项在大 batch 涨得比网络慢**，因为 M 变大让填充率改善，抵消了一部分增长。

#### （2）多专家 → 同一颗芯片：串行，这是聚类的代价

一个专家的 GEMM 需要 3,584 个瓦片，芯片只有 256 个核：

```text
3,584 ÷ 256 = 14 个 wave   →   一个专家就占满整颗芯片
C 个专家在同一颗芯片        →   14 × C 个 wave   →   时间 × C
```

**注意它的性质：不是"算力不够"，而是"一个专家就已经把机器占满了"。**

两个推论：

- 想"分散到不同的核"**没有用** —— 粒度不对，一个专家已经用掉全部核
- 只能"分散到不同的芯片"

#### （3）多 token → 同一目的芯片：合并，这是聚类的收益

MoE 分发时，一个 token 的输入向量要复制 k 份发给 k 个专家。如果几个专家在同一颗芯片上，只需要发一份。

```text
一个 token 的 7.2 个热专家：
  落在 7 颗芯片上  →  要发 7 份
  落在 1 颗芯片上  →  只发 1 份
```

### 0.3 一句话概括聚类

> **聚类的本质 = 用"多专家同芯片"的串行代价，换"多 token 少发几份"的通信收益。**
>
> 划不划算取决于三件事：
> 1. **通信有多贵** —— 取决于走哪条链路（旋钮③）
> 2. **计算有多贵** —— 取决于 C（旋钮②）
> 3. **一次要发多少份** —— 取决于 fanout

### 0.4 三个旋钮的容量账

这是讨论所有方案的前提。每个专家 42 MB，一颗类脑芯片可用 SRAM 652.8 MB，一个 node = 8 芯片。

## 1 前提：热专家放类脑，冷专家放 GPU

这是已经定下的配置。为什么这样分：

- **小 batch**（一层只用到 8–57 个专家）：瓶颈是"把专家权重从存储搬进来"，类脑的片上 SRAM 快，所以放类脑
- **大 batch**（一层用到 222–252 个专家，几乎全用上）："冷专家"基本不存在了，瓶颈变成跨芯片通信

本文只讨论**大 batch 那一段**——专家怎么摆在芯片上，能让通信少一点。

### 尺度（DeepSeek-V3，热专家按 20%）

| | 数量 |
|---|---|
| 一个专家 | 42 MB |
| 一层 256 个专家 | 10.5 GB |
| 一层里的热专家（20%） | **51 个 = 2.09 GB** |
| 全部 58 层的热专家 | 121 GB → 191 颗芯片（24 个 board） |
| 一颗类脑芯片可用 SRAM | 653 MB |

**注意：一层只有 51 个热专家要摆，不是 256 个。**

## 2 层级：node → 芯片 → 核

```text
node          8 颗芯片
  └ 芯片       256 个核，总共 768 MB SRAM
      └ 核     每个核 3 MB SRAM
```

**SRAM 是挂在核上的**，不是挂在芯片上的。这一点决定了下面第 3 节。

## 3 关键：一个专家就占满整颗芯片

**权重放得下 ≠ 算得动。** 这是两件事。

一个专家的矩阵乘法需要多少个"瓦片"：

```text
ceil(7168 / 64) × ceil(2048 / 64) = 112 × 32 = 3,584 个瓦片
芯片有 256 个核  →  3,584 ÷ 256 ≈ 14 个 wave
```

**一个专家就要让整颗芯片的 256 个核跑 14 遍。**

所以：

```text
一颗芯片放 1 个专家  →  算 14 个 wave
一颗芯片放 4 个专家  →  算 56 个 wave   （一个接一个，不是并行）
```

> 这也是为什么"把专家分散到不同的核"没用——一个专家已经把核占满了。要分散，只能分散到不同的**芯片**。

## 4 C 是什么

**C = 一颗芯片上塞几个专家。**

一层 51 个热专家，怎么摆：

| C | 用几颗芯片 | 每颗芯片要算几个专家 |
|---|---|---|
| **C = 1** | 51 颗 | 1 个（不串行） |
| **C = 2** | 26 颗 | 2 个 |
| **C = 4** | 13 颗 | 4 个 |
| **C = 8** | 7 颗 | 8 个 |

```text
C 越大  →  用的芯片越少，通信范围越小      ✓ 好
C 越大  →  每颗芯片串行算的专家越多，越慢   ✗ 坏
```

**C 就是这两头之间的旋钮。**

另外还有一条链路的门槛：

```text
落在一个 node 内（≤8 颗芯片）→ 90 GB/s，延迟 0.4 µs
跨 node                      → 39 GB/s，延迟 7 µs
                                ↑带宽差 2.3 倍，延迟差 17.5 倍
```

**所以"能不能落进一个 node"是个大台阶，比"少发几份数据"重要得多。**

## 5 聚类到底能省多少：理想 vs 现实

一个 token 要用 7.2 个热专家。**扇出 = 这 7.2 个专家落在几个 node 上。**

### 怎么算

```text
第 1 步  一层 51 个热专家，每 C 个一组  →  ⌈51/C⌉ 颗芯片
第 2 步  这些芯片占几个 node            →  ⌈芯片数 / node 大小⌉
第 3 步  一个 token 的 7.2 个专家落在这几个 node 上
```

### node = 8 颗芯片

| C | 放在几颗芯片 | 占几个 node | 每颗芯片放几个 | 一个 token 发给几颗芯片 | **落在几个 node** | 落进 1 个 node |
|---|---|---|---|---|---|---|
| 1 | 51 | 7 | 1.0 | 7.20 | **4.87** | |
| 2 | 26 | 4 | 2.0 | 6.76 | **3.57** | |
| 4 | 13 | 2 | 3.9 | 5.98 | **1.99** | |
| **7** | **8** | **1** | 6.4 | 5.14 | **1.00** | **✓** |
| 8 | 7 | 1 | 7.3 | 4.87 | 1.00 | ✓ |
| 16 | 4 | 1 | 12.8 | 3.57 | 1.00 | ✓ |

### node = 16 颗芯片

| C | 放在几颗芯片 | 占几个 node | **落在几个 node** | 落进 1 个 node |
|---|---|---|---|---|
| 1 | 51 | 4 | **3.57** | |
| 2 | 26 | 2 | **1.99** | |
| **4** | **13** | **1** | **1.00** | **✓** |
| 8 | 7 | 1 | 1.00 | ✓ |

### 两个数各自管什么

```text
"发给几颗芯片"  →  决定要发几份字节     （7.20 → 5.14）
"落在几个 node" →  决定走哪条链路       （>1 就跨 node，=1 就 node 内）
```

C=4 和 C=7 对比一下就很清楚：

```text
C=4：发 5.98 份（比 C=1 少 17%），但落在 2 个 node → 还是跨 node
C=7：发 5.14 份（少 29%），而且落在 1 个 node  → 走快链路   ← 关键在这里
```

### 门槛公式

```text
落进一个 node 需要的最小 C  =  ⌈ 一层热专家数 ÷ node 芯片数 ⌉

node = 8   →  ⌈51/8⌉  = 7
node = 16  →  ⌈51/16⌉ = 4
```

> 表中"落在几个 node"这一列是按**随机分组**算的（把 51 个专家随便 C 个一组）。
> 如果按**完美聚类**（一个 token 的专家正好被分在同一组），这一列会小很多——但真实值在两者之间，**取决于共激活结构有多成块，必须用真实路由 trace 才能确定**。

## 6 结果：不同 batch 下的实测（node = 8，紧邻放置）

| batch | 触及热专家 | C=1 | C=2 | C=4 | C=8 | 最优 |
|---|---|---|---|---|---|---|
| 1 | 8 | 61 | 118 | 235 | 470 | C=1 |
| 8 | 36 | 137 | 238 | 440 | 828 | C=1 |
| 32 | 51 | 158 | 212 | 321 | 507 | C=1 |
| 64 | 51 | 249 | 305 | 420 | 596 | C=1 |
| 128 | 51 | 420 | 467 | 568 | 674 | C=1 |
| 256 | 51 | 761 | 791 | 863 | 830 | C=1 |
| **512** | 51 | 1443 | 1438 | 1453 | **1142** | C=8（−21%）|
| **1024** | 51 | 2807 | 2732 | 2631 | **1762** | C=8（−37%）|

单位 µs，一层 MoE。

**node = 8 时，batch ≥ 512 聚类才开始划算；而且最优永远是 C=8。**

### 为什么必须是 C=8

因为 51 ÷ 8 = 6.4 → **取整后要 7 颗芯片，刚好 ≤ 8**，才跨得过 node 门槛。

```text
C=1：51 颗芯片 → 跨 7 个 node   → 走慢链路
C=2：26 颗芯片 → 跨 4 个 node   → 走慢链路
C=4：13 颗芯片 → 跨 2 个 node   → 走慢链路   ← node=16 时这里就够，node=8 时不够
C=8： 7 颗芯片 → 落进 1 个 node → 走快链路   ✓ 只有这个进得去
```

**node 从 16 缩到 8，唯一进得去的 C 从 4 变成 8，串行代价翻倍——所以表里 C=4 那一列全变差了。**

**收益的大头不是"少发几份数据"，而是"把通信从跨 node 换成 node 内"。**

## 7 减少比例是怎么算出来的：三笔账

聚类同时动了三个东西，最终的减少比例是这三个加起来的结果。

以 node = 8、一层 MoE 为例（单位 µs）：

### batch = 256

| C | 芯片数 | node 数 | 链路 | ① 网络延迟 | ② 网络字节 | ③ 计算 | 合计 |
|---|---|---|---|---|---|---|---|
| 1 | 51 | 7 | 跨 node | 14.0 | 664.4 | 80.6 | 760.8 |
| 2 | 26 | 4 | 跨 node | 14.0 | 612.0 | 161.3 | 790.8（+4%）|
| 4 | 13 | 2 | 跨 node | 14.0 | 519.2 | 322.6 | 862.7（+13%）|
| **7** | **8** | **1** | **node 内** | **0.8** | **183.3** | **564.5** | **760.7（±0%）**|

### batch = 1024

| C | 芯片数 | node 数 | 链路 | ① 网络延迟 | ② 网络字节 | ③ 计算 | 合计 |
|---|---|---|---|---|---|---|---|
| 1 | 51 | 7 | 跨 node | 14.0 | 2657.7 | 133.3 | 2806.8 |
| **7** | **8** | **1** | **node 内** | **0.8** | **733.3** | **933.2** | **1679.4（−40%）**|

（SRAM 读取那一项 = C × 0.86 µs，最大 6 µs，可以忽略，没单列）

### 三个效应

| | 是什么 | 方向 |
|---|---|---|
| ① 网络延迟 | 跨 node（7 µs）→ node 内（0.4 µs） | **省** |
| ② 网络字节 | 扇出减少 + 链路带宽变大 | **省** |
| ③ 计算 | 每颗芯片串行算 C 个专家 | **赔** |

② 这一项拆开看（C=1 → C=7）：

```text
扇出      7.20 → 5.14       少发 29%
带宽      39   → 90 GB/s    快 2.31 倍
合起来    0.71 ÷ 2.31 = 0.31    →   664.4 → 183.3（少 72%）   ✓ 对得上
```

### 净结果

```text
batch 256：
  ① 延迟    14.0 →   0.8    省   13
  ② 字节   664.4 → 183.3    省  481
  ③ 计算    80.6 → 564.5    赔  484
  ─────────────────────────────────
  净       760.8 → 760.7    打平

batch 1024：
  ① 延迟    14.0 →   0.8    省   13
  ② 字节  2657.7 → 733.3    省 1924
  ③ 计算   133.3 → 933.2    赔  800
  ─────────────────────────────────
  净      2806.8 → 1679.4   省 40%
```

**关键：② 随 batch 线性涨，③ 涨得慢。所以 batch 越大，省的越超过赔的。**

## 8 极值点：收益有上限，约 −56%

把 batch 一直扫上去，规律就出来了。**收益一路涨到 batch ~8192，然后饱和在 −56%，不再变化；最优 C 始终是 4。**

| batch | 网络(C=1) | 计算(C=1) | C=4 | 最优 | 收益 |
|---|---|---|---|---|---|
| 64 | 180 | 67 | 333 | C=1 | 0% |
| 128 | 346 | 72 | 407 | C=4 | −3% |
| 256 | 678 | 81 | 555 | C=4 | −27% |
| 512 | 1343 | 98 | 851 | C=4 | −41% |
| 1024 | 2672 | 133 | 1441 | C=4 | −49% |
| 2048 | 5329 | 204 | 2625 | C=4 | −53% |
| 4096 | 10645 | 346 | 4992 | C=4 | −55% |
| 8192 | 21276 | 629 | 9724 | C=4 | **−56%（饱和）** |

单位 µs。注意**计算项在大 batch 也会涨**（67 → 629 µs），不是常数。

> **记录到 8192 为止。** 8192 / 16384 / 32768 三组算出来都是 −56%，连续三组没有明显增长，再往上不用记了。饱和值就是 **−56%**。

### 最优 C 的规律

**永远选"刚好能让一层落进一个 node 的最小 C"：**

```text
最优 C = ⌈ 一层热专家数 ÷ node 芯片数 ⌉

node = 16  →  ⌈ 51 ÷ 16 ⌉ = 4
node =  8  →  ⌈ 51 ÷  8 ⌉ = 7
```

```text
C = 2 → 26 颗芯片 > 16  → 跨 node，走慢链路      ✗ 没拿到好处
C = 4 → 13 颗芯片 ≤ 16  → 落进一个 node，快链路   ✓ 刚好
C = 8 → 也只是快链路，但计算白赔一倍             ✗ 多余
```

**所以最优 C 是被 node 大小钉死的，它不随 batch 变。**

> 注意上面那个门槛公式给的是**最小值**：C 再大也只是浪费计算（链路已经最快了），C 小一点就跨 node。

### node=8 vs node=16：门槛差 8 倍

| batch | node=8 最优 | node=16 最优 |
|---|---|---|
| 256 | C=7（**0%**） | **C=4（−27%）** |
| 1024 | C=7（−40%） | C=4（−49%） |
| 4096 | C=7（−51%） | C=4（−55%） |

```text
              node = 8      node = 16
门槛 C         ⌈51/8⌉ = 7    ⌈51/16⌉ = 4
起点 batch      ~1024         ~128
饱和收益        ~−54%         −56%
```

**node 从 8 加到 16，门槛 C 从 7 降到 4（计算省 40%），"开始划算"的 batch 从 1024 提前到 128——差了 8 倍。**

|---|---|---|---|---|---|
| 128 | 8 | **34.7%** | 27.586 ms | 46.374 | 142.770 |
| **192** | **12** | **2.0%** | 24.282 | 43.230 | 140.571 |
| **256** | **16** | **0.0%** | 24.019 | 42.945 | 140.161 |
| 512 | 32 | 0% | 23.621 | 42.514 | 139.534 |
| 1024 | 64 | 0% | 23.423 | 42.300 | 139.226 |
| 4096 | 256 | 0% | 23.281 | 42.150 | 139.025 |

三条结论：

```text
① 容量下限 = 12 个 board（192 芯片）   134 GB ÷ 0.6528 GB = 206 颗
② 16 个 board 刚好有余量（0% spill）    ← 就是现在的配置
③ 再往上加是浪费：256 → 4096 芯片（16 倍）只快 3%
```

128 芯片（8 board）时慢 15%，那是 **spill 的代价**，不是通信的。

> 加芯片几乎没用，是因为模型里 all-to-all 用的是 `延迟 + (n-1)/n × 字节/带宽`，`(n-1)/n` 很快就趋近 1。**真实网络在芯片数很大时会有拥塞，模型没有建这一层**——这一点引用结论时要注意。

## 10 去重：模型目前没做

### 模型现在的假设

```python
disp = T * k * d * cb      # dispatch
comb = T * k * d * cb      # combine
outputs=[_a(..., T * k, d, ...)]   # 输出张量直接物化成 T×k 行
```

**永远是"每个 token 发 k 份"，跟专家摆在哪颗芯片无关、也不会因为多个专家同芯片而合并。** 这正是 Occult 说的"OLMoE/MegaBlocks 基线"。

### 这对两边的影响不一样

| | 一个 token 的专家落在几个目的地 | 模型收的 | 去重后 | 模型高估 |
|---|---|---|---|---|
| **GPU 基线**（ep=4，256 专家） | 4 × (1−C(192,8)/C(256,8)) = **3.61** | 8 份 | 3.61 份 | **2.2 倍** |
| **脑池**（C=1，每个专家独占一颗芯片） | **7.2**（没有可合并的） | 7.2 份 | 7.2 份 | 无 |

### 两边都加上去重之后

| batch | all_gpu | all_gpu 去重 | hot_cold | hot_cold 去重 |
|---|---|---|---|---|
| 1 | 4.936 ms | 4.929 ms（−0.1%）| 3.919 ms | 3.919 ms |
| 32 | 9.447 | 9.235（−2.2%）| 9.600 | 9.600 |
| 128 | 12.880 | 12.034（−6.6%）| 24.019 | 24.019 |
| 512 | 23.304 | 19.921（−14.5%）| 76.826 | 76.826 |

**GPU 基线只改善 2–15%，而不是 55%**——因为它的瓶颈根本不是 all-to-all，而是**从 HBM 读权重**；通信只占它总时间的 5–26%。

**所以结论方向没变：**

```text
batch   1 → hot_cold 快 1.26×
batch  32 → all_gpu  快 1.04×
batch 128 → all_gpu  快 2.0×
batch 512 → all_gpu  快 3.9×
```

## 11 这些考量属于哪一层

| 考量 | 属于哪一层 | 谁决定 | 编译器能动吗 |
|---|---|---|---|
| 共激活结构（谁常和谁一起出现） | **模型** | 训练出来的路由 | ✗ |
| 专家剪枝 | **模型** | 算法改动，会掉精度 | ✗ |
| **专家放哪颗芯片（C）** | **编译器** | 放置算法 | **✓** |
| **去重（同目的地只发一份）** | **编译器/运行时** | 通信算子实现 | **✓** |
| **all-to-all 的分层/分块** | **编译器** | 通信调度 | **✓** |
| **微批流水** | **编译器/调度器** | 调度 | **✓** |
| 算子融合 | **编译器** | 图优化 | ✓ |
| node 由几颗芯片组成 | **硬件** | 板卡设计 | ✗ |
| SRAM 容量 / 带宽 | **硬件** | 芯片设计 | ✗ |
| 一个专家占满 256 核 | **硬件 + 编译器** | 硬件给核数，编译器定 tile 怎么切 | 部分 |

分成两类：

```text
约束（编译器改不了）    →  共激活结构、node 大小、SRAM 容量、核数
优化空间（编译器能决定）→  专家放置 C、去重、通信调度、微批
```

**所以这是一个"编译器 × 硬件"的联合设计问题。而 FlowGPU 的角色，就是给编译器做放置决策时用的代价模型。**

## 12 关键发现：node 做大 > 聚类

> **本节和第 9 节都讲板卡，角度不同**：第 9 节讲"容量够不够"（12 board 是下限），本节讲"加多了有没有用"（没有）。第 13 节把两条并进趋势里。

按最开始（`hot_cold_probe.py`）的设置跑：`lynxi_hp300_proj`，**node = 8 颗芯片**。

### A. 加板卡完全没用

| 脑芯片 | board | C=1 | C=2 | C=4 | C=8 | C=16 | 最优 |
|---|---|---|---|---|---|---|---|
| 128 | 16 | 2807 | 2732 | 2631 | **1762** | 2598 | C=8（−37%）|
| 256 | 32 | 2807 | 2732 | 2631 | 1762 | 2598 | C=8 |
| 512 | 64 | 2807 | 2732 | 2631 | 1762 | 2598 | C=8 |
| 1024 | 128 | 2807 | 2732 | 2631 | 1762 | 2598 | C=8 |
| 2048 | 256 | 2807 | 2732 | 2631 | 1762 | 2598 | C=8 |

**从 128 到 2048 芯片（16 倍），数字一个都不差。** 因为整个计算只跟"一层 51 个热专家怎么摆"有关，跟池子里有多少芯片无关。

### B. node 大小才是关键

| node | C=1 | C=2 | C=4 | C=8 | C=16 | **最优** |
|---|---|---|---|---|---|---|
| 8 | 2807 | 2732 | 2631 | **1762** | 2598 | C=8（−37%）|
| 16 | 2807 | 2732 | **1441** | 1762 | 2598 | C=4（−49%）|
| 32 | 2807 | **1332** | 1441 | 1762 | 2598 | C=2（−53%）|
| **64** | **1288** | 1332 | 1441 | 1762 | 2598 | **C=1（不用聚类）**|
| 128 | **1288** | 1332 | 1441 | 1762 | 2598 | **C=1** |

门槛正好在 **51 = 一层的热专家数**：

```text
node < 51  →  必须聚类，C = ⌈51/node⌉，收益 37%–53%
node ≥ 51  →  C=1 就是最优，聚类完全不需要
```

node = 64 时，51 个热专家各自占一颗芯片（51 ≤ 64），**全部落在一个 node 内，而且一点都不串行**。

### 最重要的对比

```text
node =  8，聚类到 C=8   →  1762 µs
node = 64，不聚类 C=1   →  1288 µs      ← 好 27%
```

**聚类的天花板（1762）比"node 够大"（1288）还差 27%。**

因为聚类永远要赔串行（C=8 就是每颗芯片串行算 8 个专家），而 node 够大时根本不用聚，一点串行都不赔。

### 所以规律是

```text
聚类的收益 = 在 node 不够大时，强行换到 node 内链路的代价
           = 省下的网络 − 赔掉的串行

node 越大 → 需要的 C 越小 → 赔得越少 → 收益越大
node ≥ 51 → C = 1 → 一点不赔 → 收益 = 全部网络收益
```

| 做法 | 效果 |
|---|---|
| 加板卡 | **29 个 node 之前有用**（−25% → −40%），之后饱和（见 C 节）|
| 加 node 大小 | **最有效**：node 8 → 64，1762 → 1288（−27%）|
| 聚类 | 只是 node 不够大时的**补救措施** |

**如果硬件上能把 node 做到 51–64 颗芯片（而不是 8 颗），聚类这件事就不用做了，而且性能还更好。**

### C. 修正：加板卡不是"完全没用"，而是"29 个 node 之后没用"

上面 A 表说"加板卡数字不变"，**那是因为没算"包场约束"**。加上之后就变了。

**包场约束**：要让一层落进一个 node，这个 node 必须装得下这一层的全部 51 个热专家。

```text
一个 node = 8 芯片 × 15.5 个坑 = 124 个坑
一层热专家 = 51 个坑
→ 一个 node 最多给 2 层"包场"（2 × 51 = 102 ≤ 124）
→ 58 层 ÷ 2 = 29 个 node
```

**所以有两个下限：**

```text
容量下限：121 GB ÷ 5.22 GB(每 node) = 24 个 node
包场下限：58 层 ÷ 2 层每 node      = 29 个 node    ← 更紧
```

批 = 1024，node = 8：

| 池 node 数 | 芯片数 | 能包场的层占比 | **不聚类 C=1** | **聚类 C=7** | 聚类省 |
|---|---|---|---|---|---|
| 16 | 128 | 55%（容量也不足）| 2807 | 2115 | −25% |
| 20 | 160 | 69%（容量不足）| 2807 | 1981 | −29% |
| 24 | 192 | 83% | 2807 | 1847 | −34% |
| **29** | **232** | **100%** | 2807 | **1679** | **−40%** |
| 32 | 256 | 100% | 2807 | 1679 | −40% |
| 128 | 1024 | 100% | 2807 | 1679 | −40% |
| 256 | 2048 | 100% | 2807 | 1679 | −40% |

三条结论：

1. **不聚类（C=1）恒定 2807，跟池子大小完全无关** —— 因为一层要 51 颗芯片 = 7 个 node，无论池子多大都跨 node。**加池子救不了它。**
2. **聚类从 2115 降到 1679，饱和点在 29 个 node** —— 少于 29 个 node 时只有一部分层能包场，收益打折
3. **收益区间：−25%（16 node）→ −40%（≥29 node）**

**所以第 9 节和本节 A 表那个"加板卡没用"的说法要修正为：**

```text
16 → 29 个 node ：有用（−25% → −40%）
29 个 node 以上  ：没用（饱和）
```

**你们现在的 16 个 board（256 芯片 = 32 node）刚好过了 29 这条线。**

## 13 多角度扫描：五张表和六条趋势

### 先说清楚"紧邻"和"随机"是什么

聚类有两个**独立**的编译器决策，不要混：

| 决策 | 是什么 | 表里的位置 |
|---|---|---|
| **① 每颗芯片放几个专家** | 密集度 | **行**（C = 1/2/4/8/16）|
| **② 用哪些芯片** | 位置紧不紧 | **列**（紧邻 / 随机）|

**所以"随机"不是"完全不编译"**——C 一样做了，只是**没做第②项**。

```text
紧邻  = 编译器特意把这一层的芯片安排在相邻位置
       一层的 node 跨度 = ⌈芯片数 ÷ 8⌉

随机  = 没做位置优化，一层的芯片散落在整个池子里
       一层的 node 跨度 = N × (1 − (1 − 1/N)^芯片数)
                         （N = 池子里的 node 数）
```

举例（C=8，一层占 7 颗芯片，池子 32 个 node）：

```text
紧邻：那 7 颗芯片挨在一起        → 落进 1 个 node
随机：那 7 颗芯片撒在 32 个 node 里 → 落进 6.4 个 node
```

**这一列只在 C ≥ 7（芯片数 ≤ 8）时才有意义**，因为只有那时"紧邻"才能换来"落进 1 个 node"：

| C | 芯片数 | 紧邻跨度 | 随机跨度 | 时间一样吗 |
|---|---|---|---|---|
| 1 | 51 | 7 | 20.4 | **一样**（都 > 1）|
| 4 | 13 | 2 | 10.8 | **一样**（都 > 1）|
| **8** | **7** | **1** | **6.4** | **不一样**（一个 = 1）|

> **你们的默认是哪一种？需要确认。** 如果默认是"专家 i 分给 rank i"（顺序分配），一层的专家天然就挨着，"紧邻"是白拿的；如果是"让每颗芯片尽量多服务几层"（均匀铺开），那就是"随机"。**两种都会有，而这个假设会让结论差 51%。**

统一设置：`lynxi_hp300_proj`，node = 8 芯片，hot_frac=0.2，hot_traffic=0.9。单位 µs，一层 MoE。

### 表1 位置策略 × C（池 = 32 node / 256 芯片，批 = 1024）

| C | 最少需几个 node | **紧邻** | 紧邻合计 | **随机撒** | 随机合计 |
|---|---|---|---|---|---|
| 1 | 7 | 7 | 2807 | 20.4 | 2807 |
| 2 | 4 | 4 | 2732 | 18.0 | 2732 |
| 4 | 2 | 2 | 2631 | 10.8 | 2631 |
| **7** | **1** | **1** | **1679** | 7.2 | 2651 |
| 8 | 1 | 1 | 1762 | 6.4 | 2665 |
| 16 | 1 | 1 | 2598 | 3.8 | 3183 |

**只有 C ≥ 7 才进得了 1 个 node，而且必须紧邻放。** 进了 1 个 node，网络从 2091 掉到 734。

### 表2 node 大小 × C（紧邻，批 = 1024）

| C | node=8 | node=16 | node=32 | **node=64** |
|---|---|---|---|---|
| **1** | 2807 | 2807 | 2807 | **1288** ← 全局最优 |
| 2 | 2732 | 2732 | **1332** | 1332 |
| 4 | 2631 | **1441** | 1441 | 1441 |
| 7 | **1679** | 1679 | 1679 | 1679 |
| 8 | 1762 | 1762 | 1762 | 1762 |

**每个 node 大小都有自己的最优 C，node 越大最优值越好。**

### 表3 池子 node 数 × 放置策略（C=8，node=8）

| 池 node 数 | 紧邻（跨度/合计） | 随机（跨度/合计） | 随机多花 |
|---|---|---|---|
| 8 | 1.0 / **1762** | 4.9 / 2665 | +51% |
| 32 | 1.0 / 1762 | 6.4 / 2665 | +51% |
| 256 | 1.0 / 1762 | **6.9** / 2665 | +51% |

**随机撒的跨度确实从 4.9 涨到 6.9，但时间一动不动**——模型里跨度 > 1 就都算跨 node，看不见差别。

### 表4 hot_frac × C（紧邻，批 = 1024）

| hot_frac | 热专家/层 | C=1 | C=2 | C=4 | C=8 | 最优 |
|---|---|---|---|---|---|---|
| 0.02 | 5 | **1440** | 1901 | 3311 | 6295 | **C=1** |
| 0.05 | 13 | 2863 | **1453** | 1835 | 2902 | C=2（−49%）|
| 0.10 | 26 | 2825 | 2613 | **1519** | 2072 | C=4（−46%）|
| 0.20 | 51 | 2807 | 2732 | 2631 | **1762** | C=8（−37%）|
| 0.40 | 102 | 2798 | 2790 | 2793 | 2840 | 需要更大 C |

**这张验证了门槛公式**：

```text
5 个专家   → C=1（5 ≤ 8，白拿一个 node！）→ 1440，整张表最好
13 个      → C=2（7 颗芯片）
26 个      → C=4（7 颗芯片）
51 个      → C=7~8（7 颗芯片）
102 个     → 需要 C=13（表里没测到）
```

### 表5 batch × C（node=8，紧邻）

| batch | C=1 | C=2 | C=4 | C=8 | 最优 |
|---|---|---|---|---|---|
| 128 | **420** | 467 | 568 | 674 | C=1 |
| 256 | **761** | 791 | 863 | 830 | C=1 |
| 512 | 1443 | 1438 | 1453 | **1142** | C=8（−21%）|
| 1024 | 2807 | 2732 | 2631 | **1762** | C=8（−37%）|
| 2048 | 5535 | 5322 | 4992 | **3010** | C=8（−46%）|
| 4096 | 10993 | 10502 | 9712 | **5504** | C=8（−50%）|

**node=8 时，batch ≥ 512 聚类才开始划算。**

### 六条趋势

**① 最优 C = ⌈一层热专家数 ÷ node 芯片数⌉**

四个 hot_frac 全部吻合。**这个值和 batch、池子大小都无关。**

**② node 越大，最优 C 越小，全局最优值也越好**

```text
node=8  → C=8 → 1762
node=16 → C=4 → 1441
node=32 → C=2 → 1332
node=64 → C=1 → 1288   ← 最好，而且不用聚类
```

**③ 全局最优是"node 够大 + 不聚类"**

1288（node=64，C=1）比最好的聚类方案 1679（node=8，C=7）好 **23%**。

**④ 紧邻放置和聚类是两个独立旋钮，缺一不可**

```text
C=8 + 紧邻 → 1 个 node   → 1762   ✓
C=8 + 随机 → 6.4 个 node → 2665   白聚了，比 C=4 紧邻的 2631 还差
```

两种做法差 **51%**。**光聚类不做紧邻放置，等于白干。**

**⑤ batch 决定"聚类值不值"，node 决定"需要聚多少"**

```text
batch < 512  → 不值得聚
batch ≥ 512  → 值，而且越大越值（−21% → −50%）
```

**⑥ 加池子：模型里没用，物理上应该有**

随机撒时跨度从 4.9 涨到 6.9（池子从 8 加到 256 个 node），但时间不变——**因为模型的链路是二值的**。物理上跨 6.9 个 node 比跨 4.9 个慢，**这是模型的缺口**。

## 14 三个衍生方案的评估

### 14.1 想法一：冷专家也放类脑

**动机**：node 数量多的时候有富余容量，把冷专家也搬上类脑，省掉跨桥。

**容量代价**：热专家 24 node，冷专家还要 96 node → 总共 **120 node**。

**实测**（批 = 1024，node = 8）：

| 方案 | 芯片 | **总时间** | GPU | 脑 | 桥 |
|---|---|---|---|---|---|
| 热→脑，冷→GPU（现在） | 256 | 140.16 ms | 33.45 | 89.08 | 17.64 |
| **冷也上脑** | **1024** | **129.86 ms** | 23.41 | 88.81 | 17.64 |

**为什么快 7%**：GPU 侧的 MoE 从 33.45 降到 23.41 ms（省 10 ms）。冷专家的权重反正要读，放哪儿都得读，但类脑读得快（SRAM 51.2 TB/s vs GPU HBM 3.35 TB/s，差 15 倍）。

**但代价是板卡从 32 node 涨到 128 node（4 倍）。**

> **判断：7% 换 4 倍硬件，划不来。** 除非本来就有那么多 board 富余。

> **一个必须注意的坑**：这个对比很容易做错。用 `moe_offload` 跑会得到"冷专家上脑**慢 52%**"——那是因为 `moe_offload` 没把 combine 挪到 GPU，差异其实来自 **combine 的位置**，不是冷专家。正确做法是在 `hot_cold` 的基础上**只改 `moe_cold` 一条规则**。

### 14.2 想法二：重复存热专家

**动机**：某个热专家被挤爆时，多存一份分担负载。

**容量代价**：1 份 = 24 node；2 份 = **48 node**。

**收益只在"热集内部还有偏斜"时存在。** 现在主流方案（C=7）已经把整个热集压进一个 node、14 颗芯片分摊 51 个专家，在**均匀假设下负载本来就均匀，复制的收益是 0**。

**旧版模型验证不了**：旧模型假设热集内部均匀（`experts_touched` 用的是均匀路由
公式），所以复制在旧模型里恒等于 0 收益。Simulator v2 已加入 weighted/Zipf/
node-affine trace、同 node 不同芯片热副本、GPU fallback，以及
`unique-first` 对 `hot-replica-first` 的 node-count 对照；但没有真实 trace 时仍只能给
synthetic 条件结论。

> **判断：需要真实 trace 才能判断热集内部有没有偏斜。有偏斜才值得复制。**

（DeepSeek-V3 的 EPLB 就是干这个的——给高负载专家加冗余副本。但那是为了**削峰**，不是为了局部性。）

### 14.3 想法三：复制品放同一芯片还是同一 node？

三种放法，效果完全不同：

| 放法 | 收益 | 原因 |
|---|---|---|
| 同一颗芯片 | **无用** | 一颗芯片本来就被一个专家占满，多一份不解决负载 |
| **同一 node 的不同芯片** | **分摊负载，通信不变** | 两个副本都在同一个 node 内，token 用哪个都是 node 内 |
| 不同 node | **反向** | 一层就跨 node 了，通信反而变差 |

> **判断：要复制就复制在同一 node 内的不同芯片上。**

### 14.4 三个想法的共同点

```text
想法一（冷专家上脑）：动旋钮①      →  省带宽，但要多 4 倍硬件
想法二（复制热专家）：动旋钮②的容量  →  只在有偏斜时有用
想法三（复制放哪）：  动旋钮③      →  必须放在同一 node 内
```

## 15 结论
| 问题 | 答案 |
|---|---|
| 聚类能省多少 | **有上限：饱和在 −56%**（batch ≥8192）|
| 什么时候开始划算 | **node=16 时 batch ≥128；node=8 时 batch ≥1024** |
| 小 batch 呢 | **更慢**（batch 1 时 C=2 要慢 96%） |
| 为什么理想和现实差这么多 | 理想假设"一个 token 的专家正好同一组"；现实是随机分组，扇出只降 17% 不是 75% |
| 主要收益来自哪 | **换链路（node 内 vs 跨 node），不是少发字节** |
| 最优 C 是多少 | **⌈一层热专家数 ÷ node 芯片数⌉**——node=16 是 4，node=8 是 7。**不随 batch 变** |
| node 大小重要吗 | 极重要。node 从 8 加到 16，门槛 C 从 7 降到 4（计算省 40%），门槛 batch 从 1024 提前到 128 |
| 最需要的输入是什么 | **真实路由 trace**——没有它，"成块到什么程度"只能靠猜 |

## 附：几个容易绕晕的地方

**Q：一层到底用几颗芯片？**
看问的是什么。"权重放得下"最少 4 颗（2.09 GB ÷ 653 MB）；"每颗只算 1 个专家"要 51 颗。两个都对，是不同的约束。

**Q：为什么不能把一层放进 8 颗芯片？**
能放，但那 8 颗每颗要塞 6.4 个专家 → 计算串行 6.4 倍 → 赔的比省的更多（第 6 节）。

**Q：跨 node 比 node 内慢多少？**
带宽 2.3 倍，延迟 17.5 倍。延迟差得特别多，所以小 batch（通信被延迟卡住）也受影响。

**Q：C=4 是"每颗芯片放 4 个专家"，那是不是就串行 4 倍？**
是。这个代价已经算进第 6 节的表里了。
