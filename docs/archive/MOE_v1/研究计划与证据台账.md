## 0. 结论先行

本项目真正要回答的不是“类脑芯片能不能跑 MoE”，而是：

> 在 GPU HBM、类脑 DRAM、类脑 SRAM 组成的分层存储与分层网络上，面对随时间变化的专家需求，如何联合决定专家的存储层级、副本数量、node/chip 位置和迁移时机，从而在满足 SLO 的前提下减少 node 数、提高 goodput，并控制能耗与迁移抖动？

当前仓库已经完成两条重要但不同成熟度的证据线：

1. **v1 历史模型已经回答了“PD+A 式异构拆分是否自动优于纯 GPU”。** 结论是：低时延在小 batch decode 上成立；高吞吐在特定 layer-split 上可能出现；但同等投入下的高能效和低成本没有得到支持。这些结果是 projected/analytic 情景结果，不是 KA200 真机结论。
2. **v2 已建立专家级静态放置、复制、详细网络、服务调度和结果审计的软件基础。** 它支持 held-out 路由、容量区间、`tiered` GPU fallback、多 seed 区间和多条 CLI。但 v2 的现有 smoke 只证明软件能运行，不证明任何策略有科学收益。

当前最关键的三个未完成项是：

- **没有真实 router trace。** v1 的冷热集合由手工 `hot_frac=0.2` 和 `hot_traffic=0.9` 指定，不是统计推断。
- **没有完整的高阶超图聚类。** v2 统计了完整 top-k hyperedge，但 `coactivation-clustered` 放置时先展开成所有 pair；放置目标与评估 cut 不一致。
- **没有动态刷新。** 当前单次 run 只在 placement window 上求一次 placement，之后全程静态使用；迁移流量、服务干扰、版本切换和回收都不存在，因此刷新周期严格等于无穷大。

因此，现阶段可以写“机制分析和可执行研究计划”，不能写“类脑 MoE 真机加速结论”，也不能写“动态刷新已被证明值得”。

## 1. 研究定位与贡献边界

### 1.1 一句话研究问题

选择分段静态的专家布局，并在需求发生足够大的持续漂移时进行最小必要迁移，使每一段 epoch 内的放置保持确定，同时让迁移成本显式进入性能、能耗和 SLO 评价。

### 1.2 四个联合决策

| 决策层 | 要回答的问题 | 主要物理代价 |
|---|---|---|
| 存储/执行层级 | 专家从 GPU HBM、类脑 DRAM 还是类脑 SRAM 服务 | 权重读取带宽、bridge/DRAM 带宽、静态功耗 |
| 副本数量 | 哪些专家需要第 2、第 3 份副本 | SRAM 容量、装箱、batch 变小 |
| 空间位置 | 每份副本落在哪个 node、哪颗 chip | scale-up/scale-out 流量、排队、关键路径 |
| 时间刷新 | 何时改变布局、改多少、怎样切换 | 迁移字节、迁移占用的链路和服务抖动 |

四个维度必须联合评价。只报告“热专家上 SRAM”或“聚类降低扇出”而不报告容量、副本、node 数和能耗，无法支撑系统级主张。

### 1.3 预期贡献

如果实验完整，建议把贡献限定为以下几点：

1. 给出一个同时包含 tiering、replication、placement 和 refresh 的 MoE 专家布局问题。
2. 用真实 routing trace 判断专家热度、node affinity、共激活和局部路由一致性是否存在，并测量其稳定性。
3. 将“热/冷”从固定百分比改为“在目标层级、batch、拓扑和 SLO 下的边际价值”。
4. 将迁移成本作为一等公民，比较不刷新、周期刷新、任务边界刷新、漂移触发、增量刷新和 clairvoyant oracle。
5. 给出何时静态放置足够、何时必须动态调整的相变边界；负结果同样是有价值的结论。

### 1.4 明确不作为贡献的内容

- 不把 projected 的 `lynxi_hp300_proj` 写成 KA200 或任何真实芯片规格。
- 不把 v1 的 synthetic hot/cold 结果写成真实专家热度。
- 不把 v2 smoke 中的 1 层、8 专家、均匀路由结果外推到 DeepSeek-V3。
- 不在没有迁移事件模型时讨论“每步刷新”的性能。
- 不把 GPU 集群上的 Cobalt/Director 百分比直接迁移到类脑 NPU。

### 2.4 v2 smoke 结果如何解读

`.tmp-v2-final-smoke/` 中四条命令均已有输出：

| Bundle | 文件数 | 性质 |
|---|---:|---|
| `sweep` | 4 | node-count smoke |

| `tiered` | 3 | GPU fallback smoke |

这些输出使用：

- 16 个 placement token、16 个 evaluation token；
- 全部关键硬件/功耗参数标为 projected；
- uniform routing；
- 2 chip/node，仅 1–2 个 node。

典型 smoke 数值：

- 2-node distributed：`unique-balanced` 约 21,860 tok/s，`ingress-local` 约 19,471 tok/s，即 0.891×；
- 对应 4 次 seed/placement 组合的 paired speedup 95% CI 为 0.770–1.162，结论是 `inconclusive`；
- concentrated ingress 下 `ingress-local` 的 CI 为 0.623–0.875，结论是 `unsupported`；
- `hot-replica-first` 在 smoke 中只有 0.31–0.48×，原因是它只覆盖 4 个不同的脑侧专家，而 `unique-first` 覆盖 8 个；这反映的是覆盖与复制的容量取舍，不是其真实收益；
- serving 的最高测试负载 20 req/s 仍满足目标，容量全部 `right-censored`，因此不能据此比较容量。

**结论：这些 smoke 只能证明流水线可运行、指标能落盘、CI 和失败标记会生效。不能作为算法选择证据。**

### 3.2 文献综合判断

文献一致表明：

1. 专家激活存在可利用结构，但偏斜程度和局部一致性依赖模型、任务和层。
2. 热点不是 token 级固定不变，也不是只能按任务族粗略变化；需要真实 trace 同时观察短期 burst 和长期漂移。
3. 全局重排代价高，周期/事件驱动更现实；局部重平衡可以作为另一时间尺度。
4. 迁移必须与 serving 时间线重叠或明确暂停，单独报告“搬运时间”不足以证明有效性。
5. 共激活、热度、node affinity 是不同机制，必须通过正交实验分开归因。

## 4. 统一问题形式

### 4.1 变量

- `x[l,e,c,t] ∈ {0,1}`：epoch `t` 中专家 `(l,e)` 是否在 chip `c` 有完整副本。
- `r[l,e,t]`：专家副本数。
- `z[l,e,t] ∈ {HBM, DRAM, SRAM}`：主存储层级。
- `a[l,e,c,τ]`：assignment 绑定到哪个副本。
- `u[t]`：是否在 epoch 边界刷新。
- `m[t]`：从旧布局到新布局的迁移集合。

当前 v2 只有 `x` 和 `a` 的静态版本；没有 `z` 中的类脑 DRAM 档位，没有 `u`，也没有 `m`。

### 4.2 约束

- 每个专家至少一个可执行副本；
- SRAM 容量包含 activation、routing、通信 buffer 和 reserve；
- 同一 chip 不重复同一专家；
- 迁移期间新旧版本不能导致错误绑定；
- 在途请求允许完成于旧版本；
- 迁移流量与新请求流量共享链路；
- SLO 对 TTFT、TPOT 和 goodput 生效。

### 4.3 目标

不要只最小化单层 completion。建议同时输出：

- SLO goodput；
- `tokens/s/node`；
- `J/token`；
- 最小可行 node 数；
- P50/P99 latency；
- 迁移期间 violation；
- 每个 epoch 的净收益和累计收益。

推荐把主目标写成：

```text
maximize  goodput_SLO
subject to
  SRAM/DRAM capacity
  one complete replica per destination
  migration bandwidth and dual-buffer budget
  version consistency
  latency percentiles
```

并把能耗、capEx 和 node 数作为约束或并列报告，而不是将所有东西压成一个不可解释的分数。

## 5. 冷热划分：当前实现与正确做法

### 5.1 v1 的冷热是手工情景

`flowgpu/workload/llm.py:232-251` 使用：

```text
hot_frac
hot_traffic
E_hot = round(E * hot_frac)
k_hot = k * hot_traffic
```

因此历史实验中的：

- 20% 专家；
- 90% 流量；
- 51 个热专家/层；
- 2,958 个热专家；

都是模型假设，不是从 trace 统计出的结果。

### 5.2 v2 的状态

`flowgpu/sim_v2/demand.py` 统计：

- `global_assignments[(layer, expert)]`；
- `node_assignments[(home_node, layer, expert)]`；
- 完整 top-k expert set 的 hyperedge 频次。

v2 没有正式的 hot/cold 二元分类器，而是直接对连续需求排序。tiered planner 使用：

```text
score(e) = expected_assignments(e) / expert_weight_bytes
```

这是一个合理的冷启动 baseline，但还不是最终问题中的边际价值，因为它没有显式考虑：

- GPU/DRAM/SRAM 路径的单位访问成本差；
- 迁移摊销；
- capacity shadow price；
- 聚集后 `M` 变大或拆开后 `M` 变小；
- 新增副本带来的通信与批量效率变化。

### 5.3 建议的专家价值

对目标位置 `p` 和当前 placement 增加专家 `e` 的边际收益定义为：

```text
Delta(e,p) =
    reduced_weight_read_time
  + reduced_network_critical_path
  + reduced_replica_queue
  - batch_fragmentation_penalty
  - capacity_shadow_price * weight_bytes(e)
  - migration_amortized_cost(e,p)
```

“热专家”应定义为：

> 在当前 node、batch、拓扑、剩余容量和 SLO 下，进入目标层级或新增副本的边际价值为正，并且按 `Delta / bytes` 排名靠前的专家。

### 5.3.1 必须区分“缓存型”与“独占分层”语义

“HBM 放冷、SRAM 放热”有两种不同实现，不能共用一套结论：

| 模式 | HBM 内容 | 类脑内容 | 含义 |
|---|---|---|---|
| 独占分层 | 只放冷专家 | 只在 SRAM 放热专家 | 真正释放 HBM，但没有热专家 GPU fallback |
| HBM fallback | 保留所有专家 | 放热专家副本 | 不释放 HBM，只降低热专家访问成本 |

当前 v1 的 `hot_cold` 接近独占分层；当前 v2 的 `tiered_expert_plan()` 是 HBM fallback，因为
`make_gpu_tier_chip()` 要求 GPU 能容纳每个专家的一份完整 fallback。

对单个 expert assignment，应比较实际关键路径，而不是只比较峰值带宽：

```text
T_GPU(e,B) =
    HBM_weight_read(e)
  + t_gpu_expert(e,B)
  + GPU_queue

T_brain(e,B) =
    bridge_out(B)
  + max(SRAM_weight_read(e), t_brain_expert(e,B))
  + brain_network
  + bridge_back(B)
  + brain_queue
```

因此，“专家从 GPU 搬到脑侧 SRAM”并不能笼统地说成同时降低 HBM 流量和 bridge 流量：

- 它直接减少该专家的 HBM 权重重复读取；
- 它会增加 activation/result 的 bridge 往返；
- 如果冷专家原本在 GPU，而热专家在脑侧，减少冷专家 fallback 可能减少跨池切换；
- 如果只是给 HBM 中的专家增加一份脑侧副本，HBM 容量并没有释放。

现有 projected profile 中，单个 42 MiB 专家、单颗芯片、忽略延迟和争用时：

| 路径 | 带宽 | 权重读取下界 |
|---|---:|---:|
| H100 HBM → GPU | 3.35 TB/s | 13.1 µs |
| projected `hp300_proj` 芯片 SRAM | 51.2 TB/s | 0.86 µs |
| estimated KA200 SRAM | 2.4 TB/s | 18.4 µs |

这说明类脑 SRAM 的潜力真实存在，但：

1. `hp300_proj` 是 projected，不是 KA200 规格；
2. KA200 的 estimated SRAM 带宽低于 H100 HBM；
3. 一个专家只落在一颗 chip 上时，不能使用整个脑侧集群的聚合 SRAM 带宽；
4. 还要加入 bridge、node fanout、all-to-all、芯片排队和较低的计算峰值。

所以正确的研究表述是：

> 类脑 SRAM 有机会降低 memory-bound decode 的权重流时间，并在小 batch 转化为端到端低延迟；是否更快取决于 bridge、拓扑、kernel、batch 和芯片数量，而不是 SRAM 与 HBM 两个带宽数字的直接比较。

### 5.4 冷热实验的最小对照

即使最终使用连续价值，也应保留以下可解释 baseline：

| 策略 | 用途 |
|---|---|
| `no-tiering` | 全部 GPU 或全部脑侧，确认层级收益来源 |
| `unique-first` | 先保证每个冷专家至少一份脑侧副本 |
| `top-10% by p(e)` | 固定低比例热点基线 |
| `top-20% by p(e)` | 对齐历史 `hot_frac=0.2` |
| `coverage-80%` | 选最少专家覆盖 80% assignment |
| `coverage-90%` | 选最少专家覆盖 90% assignment |
| `Delta/byte greedy` | 联合边际价值基线 |
| `oracle` | 小规模穷举上界 |

所有策略使用同一 SRAM reserve、同一 node 数和同一 trace。

### 5.5 热集置信度

每层、每个专家报告：

- `p(e)` 的请求级或任务块级 bootstrap CI；
- 进入 top-k 热集的概率；
- 两个无重叠时间窗的 top-set Jaccard；
- 热度排名 Kendall/Spearman 相关；
- 冷热阈值附近专家对总收益的贡献。

如果 top-set 在窗口间高度不稳定，就不应按一次窗口的排序做昂贵的全局迁移。

## 6. 共激活与聚类：当前实现与缺口

### 6.1 原始数据保留了高阶关系

`DemandProfile` 将每个 token 在某层的 top-k 专家集合保存为一个 hyperedge：

```text
{e1, e2, ..., ek} -> count
```

这一点是正确的，也是后续做完整 hypergraph partition 的基础。

### 6.2 当前放置算法实际使用 pair

`flowgpu/sim_v2/placement.py:446-452` 中，`_pair_affinity()` 对每个 hyperedge 执行：

```text
for pair in combinations(hyperedge, 2):
    affinity[pair] += hyperedge_weight
```

所以当前 `coactivation-clustered` 是 clique expansion，而不是完整超图划分。

### 6.3 放置与评估目标不一致

`primary_coactivation_cut()` 计算：

```text
sum over hyperedges:
    weight * (number_of_distinct_locations_in_hyperedge - 1)
```

也就是说：

- placement 阶段：pairwise clique 展开；
- cut 评估阶段：完整 hyperedge；
- 最终性能：detailed event simulation。

这是审计中必须明确记录的建模差异。它可能导致“pair affinity 高但整条 top-k 超边仍分散”的放置。

### 6.4 共激活不等于共同热门

如果两个专家都热，即使独立，它们也会经常同时出现。因此不能只看 joint count。

建议同时报告：

```text
marginal:       p(e)
joint:          p(e,f)
lift:           p(e,f) / (p(e) * p(f))
Ochiai:         count(e,f) / sqrt(count(e) * count(f))
hyperedge cut:  E[distinct node/chip destinations - 1]
```

解释：

- `lift ≈ 1`：共同出现主要来自各自热度；
- `lift > 1`：存在额外正相关；
- `lift < 1`：倾向于互斥；
- Ochiai 可用于与 Cobalt 的 pair 观测对齐；
- 最终仍应以 token-level hyperedge fanout 和实际 completion 为准。

对于 placement score，更合理的加权是：

```text
support(e,f) * extra-correlation * communication_cost
```

而不是单独优化 lift。低频 pair 可能 lift 很高，但对系统几乎没有影响。

### 6.5 当前 synthetic routing 的限制

当前 `generate_weighted_trace()` 只控制每层边际专家权重和可选 node affinity。每个 top-k 样本独立加权抽取，因此：

- 可以表达边际热度；
- 可以表达 node affinity；
- 不能独立控制“在保持 p(e) 不变时增强或削弱共激活”；
- 没有专用 coactivation community generator；
- 没有 burstiness generator；
- 没有显式的 task-family mixture over time。

`generate_weighted_trace()` 的 `node_expert_multipliers` 参数存在，但配置加载和 node-sweep trace construction 没有把 node-affinity 配置全部接入。

### 6.6 聚类实验必须做的正交对照

至少四组：

1. 相同边际 `p(e)`，不同 pair/hyperedge 相关性；
2. 相同共激活强度，不同 `p(e)`；
3. 相同全局 `p(e)`，不同 node affinity；
4. 相同长时分布，不同 burst 持续时间和幅度。

否则无法区分：

- popularity placement 的收益；
- node-local placement 的收益；
- coactivation clustering 的收益；
- 复制带来的负载均衡收益。

建议最终比较：

- pairwise expansion；
- 完整 hyperedge partition；
- 热度 + node affinity + hyperedge 的联合目标；
- `small-oracle`。

## 7. 刷新：从静态模型到分段静态模型

### 7.1 当前事实

当前 v2：

- placement window 只用于生成一次 placement；
- evaluation window 使用同一个 placement；
- 不更新需求统计；
- 不创建或删除副本；
- 不模拟迁移流量；
- 不支持双缓冲或服务暂停；
- 不切换 placement 版本。

因此：

```text
T_refresh = infinity
```

当前代码能够回答“过去窗口训练的 placement 在未来漂移下是否仍有效”，不能回答“检测到漂移后是否值得迁移”。

### 7.2 三类刷新必须分开

| 类型 | 操作 | 代价 | 当前状态 |
|---|---|---|---|
| SRAM 内容替换 | 类脑 DRAM → 芯片 SRAM，换入/换出 | DRAM/SRAM 带宽、双缓冲 | 未实现 |
| node 内副本重排 | 同 node 不同 chip 增加/删除副本 | node 内链路、SRAM 写入、队列 | 未实现 |
| 跨 node 全局重排 | 专家迁移、副本创建、旧副本回收 | bridge、scale-out、全链路竞争 | 未实现 |

“刷新”不能用一个固定延迟表示。它必须由具体迁移集合、源位置、目标位置、并发链路和 overlap 模式生成事件。

### 7.3 单专家搬运下界

DeepSeek-V3 一个 expert 的 FP8 参数量为：

```text
3 * 7168 * 2048 = 44,040,192 bytes = 42 MiB
```

在未加载、无固定延迟、无写回竞争时：

| 源 → 目标 | 假设有效带宽 | 42 MiB 时间 |
|---|---:|---:|
| GPU HBM → bridge → 类脑侧 | 51.2 GB/s | 0.860 ms |
| 类脑 DRAM → 芯片 SRAM | 200 GB/s | 0.220 ms |
| node 内 chip → chip | 90 GB/s | 0.489 ms |
| 跨 node | 39 GB/s | 1.129 ms |

这些是 lower bound，不是完整刷新时间。必须再加：

- 固定延迟和 DMA 启动；
- SRAM/DRAM 写入；
- 控制路径；
- 迁移与推理共享带宽；
- 多专家并发导致的拥塞；
- 双缓冲容量；
- 版本切换和回收；
- 是否 stop-the-world。

另外，仓库现有 v2 smoke 的 bridge 是 25 GB/s，并不是上表中的 51.2 GB/s；51.2 GB/s 是待验证情景参数，必须写清来源和 sensitivity。

### 7.4 搬运总量

| 集合 | 专家数 | 42 MiB 总量 | 51.2 GB/s | 200 GB/s | 39 GB/s |
|---|---:|---:|---:|---:|---:|
| 每层 20% 热集 | 51 | 2.09 GiB | 0.044 s | 0.011 s | 0.056 s |
| 58 层热集 | 2,958 | 121.3 GiB | 2.54 s | 0.65 s | 3.34 s |
| 全模型 routed experts | 14,848 | 609.0 GiB | 12.77 s | 3.27 s | 16.77 s |

上表只适用于“所有字节经过同一条串行链路”的极端情况。若 node 本地 DRAM 并行加载，墙钟时间更接近：

```text
max_over_nodes(migrated_bytes(node) / local_bandwidth(node))
  + coordination
```

如果所有 node 最终共享一个 bridge 或 ingress，则 bridge/ingress 仍是全局瓶颈。

### 7.5 回本公式

设旧布局每步时间 `T_old`，新布局每步时间 `T_new`，迁移净成本 `C`：

```text
benefit_per_step = T_old - T_new
break_even_steps = C / benefit_per_step
break_even_wall_time = C / ((T_old - T_new) / T_old)
                    = C / relative_saving
```

如果相对收益是 10%：

| 迁移成本 | 仅回本所需稳定时间 | 迁移开销占总时长 5% | 迁移开销占总时长 1% |
|---|---:|---:|---:|
| 2.54 s | 25.4 s | 50.9 s | 254 s |
| 0.65 s | 6.5 s | 13.0 s | 65 s |

所以正确结论是：

- 桥接全热集刷新约 **十几秒到几十秒** 才开始回本；
- 若要求迁移开销被充分摊薄到 1% 左右，才需要 **分钟级的稳定布局**；
- “全量刷新一律分钟级”说得过强；
- “部分刷新只要几秒”也不成立，除非被移动的少量专家贡献了大部分新增收益。

batch 1 和 batch 1024 在相同的“相对收益百分比”下会得到相同的回本墙钟时间，这是代数上的抵消，不是巧合；但迁移占绝对时间、SLO violation 和 queueing 的影响仍依赖 batch 与到达率。

### 7.6 推荐的动态问题

滚动 horizon 上选择刷新时点：

```text
choose refresh time tau and migration set M
maximize
  integral_tau_to_tau+H [T_old(t) - T_new(t)] dt
  - migration_cost(M)
  - service_interference(tau, M)
```

实际策略可使用：

- 只在任务构成变化或检测到显著漂移时触发；
- 只在预计净收益超过阈值 `C + margin` 时触发；
- 先迁移边际收益最高的副本，达到边际收益低于成本即停止；
- 设置最短 epoch 和冷却期，避免抖动；
- 使用带置信下界的收益估计，避免被噪声触发。

### 7.7 推荐对照

| 策略 | 定义 | 角色 |
|---|---|---|
| Never refresh | 当前 v2 静态布局 | 必须的负对照 |
| Periodic | 每固定 token/step/秒刷新 | 时间周期基线 |
| Task-boundary | 任务族或 request 混合改变时刷新 | 与文献观测对齐 |
| Drift-triggered | 分布距离超过置信阈值时刷新 | 自适应基线 |
| Incremental | 每次只移动最高净价值专家 | 低成本基线 |
| Oracle | 使用未来窗口求最佳布局 | 不可实现上界 |

触发统计至少包括：

- 专家边际分布变化；
- top-hot-set Jaccard；
- node-affinity 变化；
- pair/hyperedge 分布变化；
- 当前 placement 的 remote hit、queue 和 SLO degradation；
- prefill 对 decode 的预测一致性。

不能只用单一 KL divergence。低概率专家的噪声、样本量和任务混合比例会显著影响阈值。

### 7.8 迁移期间的服务语义

必须实现并区分三种模式：

1. **Stop-the-world**：暂停相关请求，保守基线。
2. **Background**：迁移与推理共享 bridge/DRAM/node link，报告 P99、SLO violation 和 goodput 损失。
3. **Overlap in compute-bound windows**：仅在安全窗口迁移，最乐观但需明确预测失败时的回退。

推荐版本一致性流程：

1. 旧副本继续服务；
2. 后台建立新副本；
3. 新副本完整可用后发布 placement version；
4. 新请求使用新版本；
5. 在途请求继续使用旧版本；
6. 旧请求完成后回收旧副本；
7. 双缓冲不足时进入显式 stall 或 fallback。

### 7.9 刷新实验的必报指标

- 迁移字节：按 bridge、scale-up、scale-out、DRAM、SRAM 分项；
- 迁移完成墙钟时间；
- 迁移期间 P99 TTFT/TPOT；
- SLO violation 次数和 goodput loss；
- 新旧 placement 的单步收益；
- 回本步数、回本秒数；
- 整个 trace 的累计净收益；
- 每个 epoch 的刷新频率和迁移专家数；
- 能量增量；
- 旧/新副本临时占用峰值。

## 8. 研究假设与可证伪条件

### H1：静态布局在稳定任务中足够

条件：任务族和专家分布稳定，或者多个任务长期混合且混合比例不变。

证伪：即使分布稳定，静态布局仍因局部 burst、排队或 node affinity 显著劣于增量刷新。

### H2：漂移主要表现为任务构成变化，而非 token 级随机变化

条件：请求级 task block 内路由相似，跨任务族差异显著。

证伪：同一任务内短期 burst 足以使静态布局持续失效，或者跨任务族的专家集合高度重叠。

### H3：高阶共激活比单独热度更能解释聚类收益

证伪：在保持 `p(e)` 和 node affinity 后，增加 hyperedge 相关性不改善 fanout、locality 或 completion。

### H4：适量副本优于全覆盖热复制

证伪：在相同 SRAM 和副本预算下，额外副本始终不优于增加冷专家覆盖或改善聚类。

### H5：迁移只在持续漂移下回本

证伪：短时 burst 也能产生足够持续收益，或部分专家迁移在远低于全量成本时获得稳定收益。

### H6：类脑 DRAM 层能改变能效结论

证伪：即使把冷专家放在类脑 DRAM，系统能耗、chip 数和 SLO capacity 仍不优于 GPU fallback 或 pure GPU 对照。

## 9. 对比项与实验矩阵

### 9.1 外层扫描

```text
for workload in {DeepSeek-V3, Qwen3, Llama-4, ...}
  for routing in {real trace, controlled synthetic}
    for node_count in ascending grid:
      for capacity_regime in {R<1, R≈1, R>1}:
        for placement in {baselines + proposed}:
          for service in {fixed-window, continuous batching}:
            run with held-out trace
```

每个 node 数独立求解 placement。不得把一个 node 数的最优布局直接复用到另一个 node 数。

外层追加：

- strong scaling：总 token 固定，增加 node；
- weak scaling：每 node token 固定，总 token 增加；
- 两条曲线分开报告。

### 9.2 必须的 placement baseline

| 类别 | 对照 |
|---|---|
| 无结构 | `unique-balanced` |
| 层内装箱 | `layer-packed` |
| 全局热度 | `popularity-replicated` |
| ingress locality | `ingress-local` |
| 同 node 负载复制 | `node-load-replicated` |
| 共激活 | `coactivation-clustered` |
| 联合目标 | `joint-greedy` |
| 上界 | `small-oracle` |
| tier | `unique-first` vs `hot-replica-first` |

`joint-greedy` 当前主要是 API 能力，标准 CLI 的 fixed/serving 策略列表尚未把它作为可直接配置策略；完整实验前需要接入或通过专门 runner 调用。

### 9.3 机制拆解实验

每次只改变一个机制：

- 打开/关闭 dispatch dedup；
- 打开/关闭 combine reduce；
- 打开/关闭 multicast；
- 关闭同 node 热副本；
- 关闭共激活目标；
- 将 earliest-finish 换为 nearest / least-loaded；
- 将 detailed network 换为 serialized path；
- 将 `t_expert(M)` 换回解析模型；
- 将真实 trace 换为相同边际热度的 synthetic trace。

任何总加速必须分解为：

```text
spill removal
network locality
network dedup/reduction
compute load balance
batch efficiency change
queueing change
additional hardware
migration overhead
```

### 9.4 服务实验

必须覆盖：

- batch 1、8、32、128、512、1024；
- short/long prompt；
- code/math/chat/general 的稳定、渐变、突变和混合；
- Poisson arrival 与 trace arrival；
- prefill/decode 共存；
- SLO 95% attainment；
- 多 seed、warm-up、admission 和 rejected requests；
- P50/P90/P99，而不是只看 mean。

### 9.5 敏感性

- SRAM reserve：10%、15%、20%；
- expert bytes 与量化格式；
- bridge 带宽/延迟；
- scale-up/scale-out 带宽/延迟；
- ingress 数：`1/N`、`1/4`、`1`；
- kernel `M` 曲线；
- migration 可用带宽比例；
- 双缓冲容量；
- migration overlap 能力；
- task drift 幅度和 epoch 长度。

如果结论只在某一个 projected 点成立，应降级为情景结论。

## 10. 怎样做可信实验

### 10.1 四层可信度

#### A. 代码正确性

- assignment/字节/容量守恒；
- placement 只引用真实副本；
- event 时间单调；
- migration 前后副本完整；
- 版本切换没有重复或丢失 assignment；
- 2–8 chip oracle；
- fast/detailed 方向一致。

#### B. trace 统计泛化

真实 trace 不能只跑一次。建议：

- 以 request 或 task block 为 bootstrap 单位；
- 不按 token 独立重采样；
- 先做 in-distribution held-out；
- 再做 task-family shift、node-affinity shift、coactivation shift；
- 所有策略在同一 trace block 上 paired replay；
- 报告 paired speedup 95% CI；
- 多时间窗口重复，而不是随机打乱后切 train/test。

如果按 10,000 次 block bootstrap 计算，报告：

- top-hot-set membership probability；
- `p(e)` CI；
- pair lift 的 CI；
- Jaccard 稳定性；
- placement 选择的稳定性；
- completion 和 goodput CI。

#### C. workload 稳健性

至少使用：

- 1 个真实模型/真实 trace 主实验；
- 1–2 个不同专家粒度和 top-k 的模型；
- uniform 负对照；
- popularity 对照；
- node-affine 对照；
- coactivation community 对照；
- burst/drift 对照。

#### D. 硬件外部效度

没有真机数据时，所有相关结论都必须标为：

```text
software model conclusion
projected hardware scenario
```

只有完成 Tier-3 microbenchmark 和 Tier-4 端到端验证，才可写：

```text
KA200/真实数据流芯片上的实测结论
```

### 10.2 决策规则

建议预先声明：

- `supported`：paired speedup 的 95% CI 下界大于 1；
- `practically supported`：下界大于 1.05，避免统计显著但工程无意义；
- `unsupported`：95% CI 上界不大于 1；
- `inconclusive`：CI 跨过 1。

对于 J/token 等越小越好的指标，规则方向相反。

如果多个模型、多个 seed 的结论不一致，主结论必须写成条件结论，不得挑选最好结果。

### 10.3 当前 CI 的边界

现有 `v2-node-uncertainty` 只传播：

- placement seed；
- evaluation seed。

它没有传播：

- kernel 曲线测量误差；
- link 参数误差；
- trace sampling error；
- task block 相关性。

所以目前即使 CI 很窄，也只表示“对 synthetic seed 稳定”，不表示“对真实工作负载和硬件稳定”。

## 11. 分阶段研究计划

### P0：冻结语义与评价合同

需要先确定：

1. 类脑 DRAM 的共享粒度：
   - 每 chip 独享；
   - 每 node 共享；
   - 两者都建模。

   建议 MVP 先做“每 node 共享 DRAM”，并保留每 chip 独享作为敏感性对照。

2. 迁移模式：
   - stop-the-world；
   - background shared bandwidth；
   - compute-phase overlap。

   建议三种都实现，stop-the-world 作为保守下界，background 作为主结论。

3. 版本一致性：
   - 新请求新版本；
   - 在途请求旧版本；
   - 无旧请求后回收。

4. 主结论指标：
   - 最小 node 数；
   - SLO goodput；
   - J/token；
   - migration P99/SLO violation。

### P1：真实 trace 与统计层

延用 Expert Activation Patterns 论文的采集思路，至少记录：

```text
request_id
token_id
step
task_family
dataset
stage: prefill/decode
layer_id
home_node or reconstructable ingress
experts
gate_weights
timestamp/window
```

当前 `load_routing_trace_jsonl()` 只接受 `request_id`、`token_id`、`step`、`layer_id`、`home_node`、`experts`、`gate_weights`，遇到 `task_family` 等额外字段会报错。因此需要：

- 扩展可选 schema 字段；
- 对 task label 做匿名化或访问控制；
- 将 full trace 保存为 artifact，并记录 SHA-256；
- 明确 placement/evaluation 是同一拓扑下的不同时间窗口。

### P2：需求分析和统计摘要

新增产物：

- `routing_summary.json`；
- 每层 marginal popularity；
- node affinity；
- pair affinity、lift、Ochiai；
- full hyperedge frequency；
- request/window top-set Jaccard；
- burst/drift 指标；
- block-bootstrap CI。

这一步先回答：

- 热集到底有多偏；
- 热集能持续多久；
- 漂移是任务族级还是 token 级；
- 共激活是否超出热度解释；
- 不同模型是否值得做同一策略。

### P3：静态联合放置

实现并比较：

- 连续边际价值代替固定 hot fraction；
- `R<1` 的 GPU/DRAM/SRAM tiering；
- `R≈1` 的唯一副本边界；
- `R>1` 的热复制与负载分摊；
- pair clique 与完整 hypergraph partition；
- `unique-balanced`、popularity、ingress-local、layer-packed、joint-greedy 和 oracle。

交付：

- 每 node 数的最小可行 placement；
- 容量、副本和 locality；
- completion、goodput、J/token；
- 机制分解；
- 多 seed CI。

### P4：动态刷新

实现：

- epoch 边界；
- migration DAG；
- 源/目标链路；
- traffic class 竞争；
- 旧/新 copy 双缓冲；
- placement version；
- stop-the-world/background/overlap；
- drift detector；
- incremental migration；
- oracle。

交付：

- 每种触发策略的完整时间线；
- 迁移完成时间；
- P99 和 SLO；
- 回本步数/秒数；
- 累计 goodput 和能耗；
- 从不刷新的差距；
- 迁移周期最优区间。

### P5：校准和真机

- expert `t_expert(M)`：`M=1,2,4,8,16,32,64`；
- 同芯片多专家并发；
- bridge/scale-up/scale-out 的消息大小与并发；
- multicast/reduce；
- idle/compute/SRAM/DRAM/link 功耗；
- SRAM reserve 和 buffer；
- 端到端小规模验证。

验收门槛参考 `docs/sim_v2/05_calibration.md`：

- 单算子 median relative error ≤ 10%；
- p95 ≤ 20%；
- 端到端 TPOT/throughput ≤ 15%；
- bottleneck ranking 一致。

## 12. 现有结果、尚未有的结果

| 问题 | 当前是否有结果 | 结果状态 | 还缺什么 |
|---|---|---|---|
| PD+A 是否降低小 batch TPOT | 有 | v1 projected scenario，条件性支持 | 真机 kernel/链路验证 |
| layer-split 是否能超过 2× throughput | 有情景 | 已发布硬件仿真，但能耗差 | 真实拓扑和执行器验证 |
| PD+A 是否达 2× 能效 | 有 | 未复现，最好 0.44× | 类脑 DRAM tier 与真实功耗 |
| v2 能否运行静态策略 | 有 | smoke + 107 tests | 真实规模配置和完整结果 bundle |
| 固定 20% 冷热是否合理 | 否 | 只是历史假设 | 真实 trace 的 pop/coverage/stability |
| v2 是否把共激活作为超图优化 | 部分 | 保存 hyperedge，放置用 pair clique | 真 hypergraph partition |
| 复制是否有收益 | 否 | smoke 不能说明 | 真实 hot skew 与同 node batch/Kernel 效应 |
| 不刷新是否总最优 | 未知 | 静态 run 无刷新 | 漂移 trace + migration event |
| 部分刷新多久回本 | 否 | 当前仅有算术下界 | 实际 flow + serving interference |
| 动态刷新的 SLO 影响 | 否 | 无迁移事件 | stop/background/overlap 实验 |
| 不同 node 数的饱和点 | 否 | 只有 1–2 node smoke | node 数 sweep + CI |
| 真实 trace 的统计 CI | 否 | synthetic seed CI only | block bootstrap |
| KA200 真机结论 | 否 | 无原始测量 artifact | Tier-3/4 校准 |

### 12.1 现在可以说

- 低时延机制在 v1 的某些小 batch 情景成立；
- PD+A 不是自动万能拆分；
- 类脑 SRAM 覆盖的容量、静态功耗和副本会显著改变吞吐/能效；
- v2 已经具备实现严格 held-out 静态专家放置实验的软件基础；
- 真实文献支持任务族漂移、共激活、复制和在线迁移值得研究；
- 没有真实 trace、DRAM tier 和 migration event 时，不能给出动态放置的确定结论。

### 12.2 现在不能说

- “真实 MoE 热专家就是 20%/90%”；
- “热专家每 N 秒刷新一次最优”；
- “pairwise 共激活等于超图最优放置”；
- “迁移在后台一定只有几毫秒”；
- “部分刷新 5% 专家就能获得全量 10% 收益”；
- “类脑 DRAM 只有 200 GB/s，因此节点内并行也一定得到这个时间”；
- “v2 已支持动态刷新”；
- “KA200 获得 x 倍加速”。

## 13. 论文层面的叙事与意义

### 13.1 推荐主线

```text
问题
  MoE decode 权重流和动态路由使容量、通信、负载和热点随时间共同变化
    ↓
观察
  真实专家激活有偏斜、任务族漂移、node affinity、共激活和局部一致性
    ↓
方法
  时间分层的联合放置
  - 连续边际价值决定 tier
  - 超图/通信决定空间聚类
  - replica budget 决定副本
  - drift-triggered incremental refresh 决定时间变化
    ↓
评价
  held-out / 时间因果切分 / paired replay
  同 node 数、同能耗账、同 trace
    ↓
结论
  找出静态放置足够、必须刷新和刷新不划算的边界
```

### 13.2 为什么有意义

这项工作把常见的二选一问题：

> “把专家放到 GPU 还是类脑芯片？”

改造成连续系统问题：

> “在每个时间区间里，哪些专家放哪一层、放几份、放哪里，以及何时值得改变？”

这比单纯做一个更快的模拟器更有研究价值，因为它能够给出：

- 硬件设计边界：node 大小、SRAM/DRAM 容量比、bridge；
- 编译/运行时边界：聚类、复制、调度和刷新；
- 工作负载边界：哪些模型和任务族值得动态放置；
- 负结果：什么时候不迁移才是最优；
- 可检验的主张：在同硬件、held-out 和详细网络下仍然成立。

### 13.3 预期图

1. 真实 trace 的专家热度、任务族相关性和时间稳定性；
2. marginal / pair / lift / hyperedge 的不同统计；
3. capacity regime 与 node 数相图；
4. placement 策略的 fanout、locality、goodput 和 J/token；
5. migration cost 与稳定 epoch 时长的回本边界；
6. refresh policy 的累计收益和 SLO violation；
7. hardware sensitivity：bridge、DRAM、SRAM reserve、node size。

## 14. 实施优先级

### 最高优先级

1. 获得至少一个真实 MoE 的 request-ordered trace；
2. 建立 hotness/lift/Jaccard/drift summary；
3. 把 `task_family` 和可选 trace 字段加入 schema；
4. 实现类脑 DRAM tier；
5. 实现 migration event 和版本切换；
6. 用真实 trace 跑 `never/periodic/task-boundary/drift/incremental/oracle`。

### 次高优先级

7. 完整 hypergraph partition；
8. coactivation-controlled synthetic generator；
9. task-block bootstrap；
10. per-case 完整 bundle；
11. node-count saturation gate。

### 真机前不必阻塞软件主线的项

- cycle-level NoC；
- 单专家跨芯片 TP；
- 完整 prefill/decode 抢占；
- speculative decoding；
- 故障恢复；
- 多租户。

这些应作为扩展，不应替代对真实 trace、DRAM tier 和迁移成本的处理。

## 15. 建议的最终验收问题

在开始正式写论文前，逐项回答：

1. 在真实 trace 中，专家热度是否比 uniform/weighted synthetic 更偏、更稳定？
2. 在保持 `p(e)` 不变时，hyperedge 结构是否仍能降低 node fanout？
3. 副本收益是否来自负载均衡，而不是仅仅因为减少了远程访问？
4. 在相同 node 数和容量下，DRAM tier 是否改善了 J/token，而不只是把桥接流量搬走？
5. 每增加一个 node，`tokens/s/node` 和 goodput 的 CI 是否仍改善？
6. 迁移的完整时间线是否进入 serving 指标，而不是事后相加？
7. 不刷新、周期刷新和任务边界刷新，在何种 drift 强度下交叉？
8. 结论是否在 bridge、DRAM、SRAM reserve、node size 和 kernel 曲线上稳定？
9. 所有决定性参数是否可追溯到 measured/vendor/paper，而不是 projected？
10. 如果没有正结果，负结果是否仍然清楚回答了“何时不值得做”？

只有这些问题都有可复现答案，才算完成从“模型设想”到“可信研究结论”的转变。
